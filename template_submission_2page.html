PART 1 - DEBUGGING
1. Why the patient was called again
  1. At 10:02:19 the call was answered and a 45-second timer started.
  2. The caller kept speaking, but nothing cancelled the timer.
  3. At 10:03:04 it fired mid-call, marked the job failed, set attempts=1 and queued a retry for +30 minutes.
  4. The call then ended answered, so the job became completed. The queued retry was never cancelled.
  5. A duplicate webhook (40 ms later) pushed attempts to 3.
  6. At 10:33:04 the retry ran. run_job does not check state, so it dialled a completed job.
2. Problems, in the order I would fix them
  1. run_job dials without checking state or attempts.
  2. The no-response timer is not cancelled on speech or call end (stale timer).
  3. No state rules: failed and completed overwrite each other, and a finished job's retry is not cancelled.
  4. Duplicate webhooks are not deduplicated (no event ID), which inflates attempts.
  5. Attempts are counted in two handlers instead of once per dial.
  6. Read-modify-write with no transaction, so the timer and a webhook can race.
  7. The phone number is logged in plain text.
3. Fix for problem 1

Claim the job atomically before dialling. Retry scheduling sets the state back to queued.

UPDATE jobs SET state='dialling', attempts=attempts+1
WHERE id=? AND state='queued' AND attempts<max_attempts

If zero rows change, log "skipped" and return without dialling. Two workers cannot both claim the job, and a completed job or one at max attempts is never dialled.

4. How a duplicate request could be detected

Looking strictly at the tool: both requests show the exact same JSON body ({"call_id": "call_8841", "status": "answered", "duration_secs": 42}), same HTTP method (POST), same IP (223.196.192.216), and identical Content-Length (67 bytes). They only differ by arrival timestamp (14:36:42 vs 14:36:57 GMT) and the tool's internal request UUID. A server seeing identical body fields for the same call_id knows the second request is a duplicate.

5. What I would add to the request

An Idempotency-Key or X-Event-ID header (e.g. Idempotency-Key: evt_8841_call_ended) and X-Delivery-Attempt: 2, allowing the server to deduplicate requests via an O(1) cache lookup before even parsing the body.

6. What I learned

Duplicate webhooks carry identical business payloads but distinct transport-level metadata (different TCP ports and server-assigned request IDs), so deduplication must happen at the application layer. Also, Windows PowerShell strips raw double quotes from JSON arguments passed to external CLI tools like curl unless single-quoted or escaped.

PART 3 - SMALL SERVICE
1. Version 1

First untouched AI-generated code: version1.py (GitHub)

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from typing import Optional

app = FastAPI()
calls_db = {}  # In-memory dict

class CallEndedPayload(BaseModel):
    call_id: Optional[str] = None
    status: str
    duration_secs: int

@app.post("/call-ended")
def call_ended(payload: CallEndedPayload):
    if not payload.call_id:
        raise HTTPException(status_code=400, detail="Missing call_id")
    if payload.call_id in calls_db:
        return {"status": "success", "message": "Call already recorded", "data": calls_db[payload.call_id]}
    record = payload.dict()
    calls_db[payload.call_id] = record
    return {"status": "success", "message": "Call recorded", "data": record}

@app.get("/calls/{call_id}")
def get_call(call_id: str):
    if call_id not in calls_db:
        raise HTTPException(status_code=404, detail="Call not found")
    return calls_db[call_id]

4. What changed (2-3 lines)

1. Replaced ephemeral in-memory dict with SQLite persistent storage using PRIMARY KEY (call_id) and atomic INSERT OR IGNORE to eliminate race conditions under concurrent webhook arrivals.
2. Upgraded to Pydantic v2 validation enforcing non-blank call_id and non-negative duration_secs, returning structured HTTP 400 Bad Request errors.
3. Standardized HTTP status codes: returning HTTP 201 Created on fresh inserts and HTTP 200 OK on idempotent duplicate replays.

PART 4 - REFLECTION
1. AI mistake

The AI initially used an in-memory dictionary with a Python check (if call_id in calls_db:). In an async multi-worker setup, duplicate webhooks arriving milliseconds apart (like the two 40ms apart in Part 1) cause a race condition where both check before either writes, creating duplicates. I replaced this with an SQLite database using an atomic PRIMARY KEY and INSERT OR IGNORE query to enforce idempotency at the database engine level.
